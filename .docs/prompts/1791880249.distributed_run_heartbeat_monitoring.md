# Distributed Run Heartbeat Monitoring

## User Request
"Please add a heartbeat to this run, so i can run it in a distributed way"

## Context
When running hyperparameter optimization studies across multiple distributed workers (e.g. across Google Colab instances, cloud VMs, or parallel processes) backed by shared RDB storage (PostgreSQL, MySQL, or network-shared SQLite):
1. Workers may crash, get preempted, or disconnect while a trial is in `RUNNING` status.
2. Without a heartbeat mechanism, those trials remain orphaned zombies indefinitely.
3. Multiple workers starting simultaneously may duplicate manual seed trial enqueues (`study.enqueue_trial`).

## Implementation Details
1. **`src/yoda/hyperopt/optuna.py`**:
   - Updated `init_study_and_metadata` to configure `optuna.storages.RDBStorage` with `heartbeat_interval` (default: 30s), `grace_period` (default: `2 * heartbeat_interval`), and `RetryHeartbeatStaleTrialCallback(max_retry=3)`.
   - Added startup stale-trial cleanup via `fail_stale_trials(study)` so aborted zombie trials are immediately failed and requeued upon worker start.
   - Configured SQLite connection timeout (`timeout=60.0`) to prevent file lock contention across concurrent workers.
   - Added `--heartbeat-interval` and `--grace-period` CLI flags in `build_base_study_parser`.
2. **`experiments/optuna_study_focused.py`**:
   - Forwarded `heartbeat_interval` and `grace_period` arguments into `init_study_and_metadata`.
   - Made champion Trial #40 baseline point enqueuing idempotent so multiple distributed workers do not enqueue duplicate baseline trials.
3. **Tests**:
   - Added `test_init_study_and_metadata_heartbeat` and `test_build_base_study_parser_heartbeat_flags` to `tests/test_hyperopt.py`.
   - Verified all 177 tests passing.
